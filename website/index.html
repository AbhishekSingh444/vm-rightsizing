Risk-Quantified Virtual Machine Right-Sizing for Private Cloud Capacity Reclamation

Abhishek Singh (23BCE5044) · Purusharth Kumar (23BCE1908)

Right-sizing tools report how much capacity they save but not how many VMs break as a result. We report both numbers together.

How we did it

    Review 1

    Literature gap table

    Recent work on cloud sizing. Every paper reports savings or accuracy; none counts the violations its reclamation causes.

    Review 1

    Problem statement and hypotheses

    The problem in our words, and three claims fixed before running the experiment.

    Problem: right-sizing tools report capacity saved but never the risk of running out. An operator cannot judge whether a recommendation is safe.
    H1

    At equal risk, M(ε) reclaims ≥ 15% more vCPU-hours and ≥ 10% more GB-hours than P95.

    H2

    The predicted risk ε matches the measured violation rate (binomial test, ECE < 0.05).

    H3

    ≥ 25% of vCPU-hours and ≥ 20% of GB-hours can be reclaimed with zero violations.

    Condition: Bitbrains fastStorage, 21-day observation / 9-day evaluation, flavour catalog vCPU {1,2,4,8,16}, memory {2,…,64} GB.
    Violation: memory: over allocation at any sample (the process is killed) · CPU: over allocation for ≥ 2 consecutive samples (slowdown).

    Review 2
    
  
    Threats to validity
    
  
    What our setup cannot prove.
    
  
    
    
    TypeThreat
    
    
    ConstructThe CPU violation rule is not validated on the cluster, and trace demand is clipped at the original allocation.
    
    
    InternalDuplicate zero rows inflate the sample count on 65 VMs.
    
    
    ExternalOne provider, one month per fleet, 5-minute sampling hides short bursts, and the Azure trace has no memory data.
    
    
    ConclusionThe bootstrap covers VM sampling only, the splits overlap by 74%, and the ECE test is too weak to reject.
    
    
    TestbedThe cluster runs at 1/16 scale: it validates memory kills, not CPU or absolute savings.
